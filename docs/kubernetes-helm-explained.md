# NepalStay Kubernetes + Helm Explained

This document explains the Kubernetes and Helm setup in `helm/nepalstay/` in plain language.
It covers:

- what each resource does
- why it exists
- how it works in the app
- the main reason to use it

## Big Picture

Kubernetes is being used here to:

- run the Next.js app as a scalable containerized service
- keep secrets out of the image and inside AWS Secrets Manager
- sync those secrets into Kubernetes safely with External Secrets Operator
- expose the app through a Service and Ingress
- keep the app reliable with probes, rolling updates, HPA, PDB, and NetworkPolicy

Helm is being used to:

- template the manifests
- keep repeated values in one place
- make deployment configurable per environment

## Chart Files

### `Chart.yaml`

```yaml
apiVersion: v2
name: nepalstay
description: Nepalstay hotel booking application
type: application
version: 1.0.0
appVersion: "1.0.0"
```

- `apiVersion: v2`
  - What: declares the Helm chart format version.
  - Why: Helm needs this to understand the chart structure.
  - Main point: tells Helm this is a modern Helm 3 chart.

- `name: nepalstay`
  - What: the chart name.
  - Why: Helm uses this as the release/chart identity.
  - Main point: names your package.

- `description: Nepalstay hotel booking application`
  - What: short human-readable description.
  - Why: makes the chart easier to understand in listings.
  - Main point: documentation for humans.

- `type: application`
  - What: tells Helm this is an app chart, not a library.
  - Why: application charts render Kubernetes resources.
  - Main point: this chart deploys workloads.

- `version: 1.0.0`
  - What: chart version.
  - Why: Helm tracks chart changes with versions.
  - Main point: versioning the deployment package.

- `appVersion: "1.0.0"`
  - What: the app version the chart targets.
  - Why: separates chart version from app version.
  - Main point: shows which app build the chart expects.

### `values.yaml`

```yaml
namespace:
  create: false

image:
  repository: 289050430809.dkr.ecr.us-east-1.amazonaws.com/nepalstay
  tag: sha-079dd13
  pullPolicy: IfNotPresent

service:
  port: 3000

ingress:
  enabled: true
  className: alb
  host: nepalstay.com
  healthcheckPath: /

secretStore:
  name: nepalstay-aws
  region: us-east-1

externalSecret:
  name: nepalstay-env
  targetSecretName: nepalstay-secrets
  remoteKey: nepalstay/prod/app

configMap:
  name: nepalstay-config
  nodeEnv: production
```

- `namespace.create: false`
  - What: disables namespace creation by default.
  - Why: the namespace already exists in your cluster.
  - Main point: avoids duplicate namespace resources.

- `image.repository`
  - What: container image registry path.
  - Why: tells Kubernetes which image to run.
  - Main point: points to the production build.

- `image.tag`
  - What: image tag.
  - Why: chooses the exact image version.
  - Main point: deploys a known build.

- `image.pullPolicy: IfNotPresent`
  - What: only pull if the image is not already on the node.
  - Why: saves time and bandwidth.
  - Main point: standard production-friendly pull behavior.

- `service.port: 3000`
  - What: service port.
  - Why: Next.js listens on 3000 in your image.
  - Main point: exposes the app port consistently.

- `ingress.enabled: true`
  - What: turns ingress on.
  - Why: you want external traffic through ALB.
  - Main point: exposes the app to the internet.

- `ingress.className: alb`
  - What: use the AWS Load Balancer Controller Ingress class.
  - Why: this creates an AWS ALB.
  - Main point: integrates Kubernetes with AWS load balancing.

- `ingress.host: nepalstay.com`
  - What: public domain name.
  - Why: ingress needs a hostname rule.
  - Main point: this is the DNS name users visit.

- `ingress.healthcheckPath: /`
  - What: ALB health check path.
  - Why: the deployed image returns 200 on `/`.
  - Main point: lets the load balancer verify the app is alive.

- `secretStore.name`
  - What: name of the External Secrets `SecretStore`.
  - Why: ExternalSecret references it.
  - Main point: connects ESO to AWS Secrets Manager.

- `secretStore.region`
  - What: AWS region.
  - Why: ESO must know where the secret lives.
  - Main point: points the secret provider to the right AWS region.

- `externalSecret.name`
  - What: Kubernetes ExternalSecret object name.
  - Why: Helm creates and manages this resource.
  - Main point: ESO sync configuration object.

- `externalSecret.targetSecretName`
  - What: Kubernetes Secret generated by ESO.
  - Why: the app reads secrets from this secret.
  - Main point: this is what the pod actually needs.

- `externalSecret.remoteKey`
  - What: AWS Secrets Manager secret name/path.
  - Why: ESO fetches data from this AWS secret.
  - Main point: source of truth for runtime secrets.

- `configMap.name`
  - What: ConfigMap object name.
  - Why: the deployment imports it using `envFrom`.
  - Main point: stores non-sensitive env values.

- `configMap.nodeEnv`
  - What: non-secret environment value.
  - Why: app needs production mode.
  - Main point: keeps basic config out of the secret store.

### `templates/externalsecret.yml`

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: {{ .Values.externalSecret.name }}
  namespace: {{ .Release.Namespace }}
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: {{ .Values.secretStore.name }}
    kind: SecretStore
  target:
    name: {{ .Values.externalSecret.targetSecretName }}
    creationPolicy: Owner
  dataFrom:
    - extract:
        key: {{ .Values.externalSecret.remoteKey }}
```

- `kind: ExternalSecret`
  - What: syncs external secret data into Kubernetes.
  - Why: app containers cannot read AWS Secrets Manager directly.
  - Main point: bridges AWS and Kubernetes secrets.

- `refreshInterval: 1h`
  - What: refresh every hour.
  - Why: keeps secrets up to date.
  - Main point: periodic secret sync.

- `secretStoreRef`
  - What: points to the SecretStore resource.
  - Why: tells ESO which provider config to use.
  - Main point: connects the sync config to AWS.

- `target.name: nepalstay-secrets`
  - What: generated Kubernetes Secret name.
  - Why: the deployment references this secret.
  - Main point: this is what pods consume.

- `creationPolicy: Owner`
  - What: ESO owns the secret.
  - Why: cleanup and lifecycle are managed automatically.
  - Main point: lets ESO control the generated secret.

- `dataFrom.extract.key`
  - What: extracts all key-value pairs from one AWS secret.
  - Why: your AWS secret is JSON-shaped.
  - Main point: one AWS secret becomes one Kubernetes secret.

### `templates/ingress.yml`

```yaml

  name: nepalstay
  namespace: {{ .Release.Namespace }}
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing

      [{"HTTP":80},{"HTTPS":443}]
    alb.ingress.kubernetes.io/ssl-redirect: "443"

  ingressClassName: {{ .Values.ingress.className }}
  rules:
    - host: {{ .Values.ingress.host }}

                port:
```

- `kind: Ingress`

  - `listen-ports`
    - What: enables HTTP and HTTPS listeners.

  - `ssl-redirect: "443"`
    - What: redirect HTTP to HTTPS.

  - `healthcheck-path`
    - What: ALB health check endpoint.

  - `healthcheck-port: traffic-port`
    - What: use the service traffic port.

- `ingressClassName: alb`

- `host: {{ .Values.ingress.host }}`

## Why these pieces matter together

- `ConfigMap` gives non-secret runtime config.
- `SecretStore` tells ESO where AWS secrets live.
- `ExternalSecret` syncs AWS data into Kubernetes secrets.
- `Deployment` runs the app pods.
- `Service` gives a stable in-cluster endpoint.
- `Ingress` exposes the app publicly.
- `HPA` scales the app with demand.
- `PDB` protects uptime during maintenance.
- `NetworkPolicy` narrows allowed traffic.

## Main Point of Using Kubernetes Here

The main goal is to make the app:

- repeatable to deploy
- secure by default
- scalable when traffic grows
- resilient when pods or nodes fail
- maintainable across environments

## Important Runtime Lessons From This Setup

- Helm can install successfully even if the app still fails at runtime.
- A pod can enter `CreateContainerConfigError` when a referenced secret is missing.
- External Secrets Operator must be healthy and able to read AWS.
- Health probes must match what the image actually serves.
- The public domain should be stored in one place, ideally Helm values and app env.

## Suggested Production Flow

1. Push the app image.
2. Update Helm values with the new image tag.
3. Run `helm upgrade --install`.
4. Confirm `SecretStore` is `Valid`.
5. Confirm `ExternalSecret` is `SecretSynced`.
6. Confirm pods are `Ready`.
7. Confirm ingress has an address.
